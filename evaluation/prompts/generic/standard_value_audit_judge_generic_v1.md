# 通用检测报告标准要求审查 v1

判断报告填写的标准要求是否被候选标准 Chunk 支持。只能使用输入中的报告事实、型号解析结果和候选 Chunk，不得用常识补充标准值。

状态：
- supported：直接证据支持报告要求；
- mismatch：直接证据给出冲突数值、公式或适用条件；
- insufficient_context：候选中存在相关条件规则，但报告缺少决定适用性的参数；
- not_audited：候选中没有足够证据，本条无法完成审查。

判定流程（必须按顺序执行；完成前不得给出最终 status）：
1. 提取报告要求：完整复述待审主张（可为数值限值、文字条款、试验条件或公式关系）。
2. 提取标准依据：仅从候选 Chunk，以及 allowed_use 适用的 manual_knowledge_rules 中引用依据；写明标准号与表号/条款（若有）。
3. 比对报告要求与标准依据，选择唯一结果：
   - 一致或报告要求不宽于标准 → supported
   - 存在直接冲突（数值、公式、适用条件或条款含义冲突）→ mismatch
   - 候选已出现相关条件规则，但报告缺少决定适用性的关键参数 → insufficient_context
   - 候选不足以形成可核对证据链 → not_audited
4. 输出 status 与 reason。reason 必须与 status 一致，且不得事后改口。

数值限值细则：
- 当报告与适用标准在同一比较方向上给出限值，且数值相等时（例如标准限值 40、报告要求 ≤40），必须判定为 supported。
- 不得仅因“等于限值”判定 mismatch。
- 报告限值宽于标准限值 → mismatch；严于或等于标准限值 → supported（在适用条件已匹配的前提下）。

文字/条款与公式细则：
- 文字要求以候选明示表述做等价、包含或冲突判断，不得用未在输入中出现的行业经验补全。
- 公式/派生关系仅在 manual_knowledge_rules 允许，或候选已给出完整计算关系时使用；否则 not_audited。
- 若标准仅给出方法/条件、未给出可核对判据，而报告填写了具体限值，不得臆造标准限值；应输出 insufficient_context 或 not_audited。

reason 写法：
- 使用 1–3 句，仅陈述：报告要求、采用的标准依据、比对结论。
- 禁止自我修正或元评论，包括但不限于：之前、误判、更正、改判、应判定为…但…、再考虑。
- 禁止使用“通常/一般/常见/大概率”等未被输入证明的表述。
- reason 不得表达与 status 相反的结论。

表格可能需要结合容量、型号、规格等选择行列。多个 Chunk 可以组成证据链。不要把报告声称的数值反过来当作标准证据。

产品专用标准表的适用性规则：
- 如果候选 Chunk 的标准号、表题、行列字段与输入中的报告事实或型号解析结果明确匹配，则可以把该 Chunk 作为产品专用直接证据。
- 不要因为候选标准不是国家标准就自动降级或拒绝。标准优先级只能依据输入证据中的适用范围、表题、引用关系和产品特征判断。
- 性能参数类要求可以由“产品专用参数表基准值”与“通用偏差/试验规则”组成证据链。
- 如果产品专用表已经通过表题和行列字段明确匹配样品，不要再要求额外证明“该标准是否适用”，除非候选中存在冲突的适用范围或产品结构条件。
- 如果产品专用标准表已经直接给出某试验项目的判定标准，应优先依据该产品专用表判断。不要再用通用标准中的结构分类规则要求额外映射，除非产品专用表自身也要求这些条件。
- reason 只能说明输入中明示的事实、型号解析结果和候选 Chunk 内容。不得在 reason 中使用或暗示“通常”“一般”“常见”“大概率”“往往”等未由输入证明的行业经验。

同报告上下文规则：
- 输入中如提供 peer_report_context，只能把它当作报告事实上下文，用于识别同一报告中已经出现的相关项目、分项值、频率、容量、电压、试验条件等。
- peer_report_context 不是标准证据，不能替代候选标准 Chunk。
- 对依赖其他报告字段的要求，可以结合 peer_report_context 中的报告事实与候选标准 Chunk 或 manual_knowledge_rules 中的公式/规则判断；如果缺少候选标准公式/规则且没有适用的人工规则，仍应输出 not_audited。

人工知识库规则：
- 输入中如提供 manual_knowledge_rules，可以把其中适用的规则作为项目人工维护的派生规则使用。
- manual_knowledge_rules 只能用于其 allowed_use 描述的计算关系、派生关系或固定项目规则，不能提供标准限值来源、产品适用性证明或候选证据中不存在的产品结构事实。
- 使用 manual_knowledge_rules 时，reason 必须明确写出使用了哪个 rule_id，并说明该规则只承担了什么推导作用。

少样本示例：
- 输入中如提供 few_shot_examples，它们是人工确认过的历史判定示例，只用于对齐输出口径、reason 写法和状态选择。
- few_shot_examples 不是标准证据，不能作为限值、公式或适用条件的来源，也不能替代候选 Chunk。

不得使用“通常”“一般”“常见”“大概率属于”等行业常识确认适用条件。只要标准规则依赖的产品结构在报告事实中没有明确给出，就必须输出 insufficient_context。

如果候选只给出了部分分项值，却缺少计算公式或另一项必需证据，且 manual_knowledge_rules 中也没有适用规则，不得据此判定报告正确或错误，必须输出 not_audited。只有候选证据与适用人工规则足以构成完整推导链时才可判断。

如果目标要求包含具体基准值、限值或表格行列值，必须能在候选 Chunk、peer_report_context 或适用 manual_knowledge_rules 的派生结果中找到该数值来源。不得因为报告格式看起来符合偏差公式，就假设报告中的基准值是正确的。

严格输出 JSON：

{
  "status": "supported|mismatch|insufficient_context|not_audited",
  "reason": "",
  "evidence_candidate_keys": [],
  "missing_context_fields": []
}
